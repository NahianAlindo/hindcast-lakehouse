# Hindcast — Forecast-Verification Lakehouse

**A pivot plan replacing the Spotify data domain with OpenWeatherMap. Stack, infrastructure, and $0 discipline carry over unchanged; the business process and dimensional model are redesigned from scratch.**

---

## 1. Project Pitch, Codename, Effort

### Codename: `hindcast` (repo: `hindcast-lakehouse`)

*Hindcasting* is the real meteorological practice of scoring a forecast against what actually happened. It names the analytical hook exactly, it's a term a domain-literate reviewer will recognize, and it preserves the `-lakehouse` suffix convention from the previous codename.

Runners-up considered and rejected: `brier-lakehouse` (too obscure without explanation), `skillscore` (reads like a sports app), `isobar` (pretty, says nothing about the pipeline).

### The pitch

> **Hindcast is an end-to-end lakehouse that grades the weather forecast.**
>
> Every three hours it captures OpenWeatherMap's 5-day/3-hour forecast for a curated set of personally-meaningful locations — the cities I've lived in, the ones my family is in, the ones I travel to. Every thirty minutes it captures what the weather *actually* did. It then joins the two across time to answer a question a plain weather dashboard structurally cannot: **how much worse is a 96-hour-ahead forecast than a 24-hour-ahead one, and does that gap depend on the city, the season, or the kind of weather being predicted?**
>
> The centrepiece is an **accumulating snapshot fact table**: one row per (location, future 3-hour slot), created the moment that slot first appears on the 5-day horizon, then rewritten roughly forty times as successive forecasts revise the prediction, and finally closed when the observed actual lands. Each row is a complete, auditable record of how a belief about the future converged on reality.
>
> Accuracy is reported as **skill relative to a persistence baseline** ("tomorrow will be like today"), not as a bare error number — because an error number without a baseline is not analysis.

### Why this isn't "another weather dashboard"

| Generic weather project | Hindcast |
|---|---|
| Shows current + forecast conditions | Shows *forecast error*, which requires two ingestion streams and a temporal join |
| Facts are a plain transaction grain | Flagship fact is an accumulating snapshot with in-place MERGE updates |
| Data is a live read-through of the API | Data has a **history the API cannot give you** — OWM does not sell you its own past forecasts, so the archive of what was predicted is created *by the pipeline* and exists nowhere else |
| Metrics are temperature and rainfall | Metrics are MAE/bias/RMSE by lead time, **Brier score** on precipitation probability, **CSI** on rain/no-rain, skill vs. persistence |
| Arbitrary top-50 city list | Curated personal-geography list with a narrative |

The third row is the differentiator worth leading with in interviews: **the dataset is generated by the act of running the pipeline.** If the pipeline stops, the data stops existing. That is not true of a Spotify charts scrape, and it makes the orchestration reliability story load-bearing rather than decorative.

### Effort

| | |
|---|---|
| **Total build effort** | ~105–125 hours |
| **Calendar** | 10 weeks at 10–12 h/week |
| **Hard calendar floor** | **~7 weeks**, not because of build effort but because the analysis needs ≥5 days of accrual to have any 120h-lead data at all, and ≥3–4 weeks to have enough slots for credible per-city, per-condition breakdowns |

**The single most important planning consequence of this pivot:** unlike the Spotify design, where `recently-played` handed you history on day one, **Hindcast's core dataset accrues in wall-clock time.** Ingestion must go live at the end of Week 2 and run continuously while Phases 3–10 are built around it. This is called out again in §12 as the critical path.

## 2. Executive Design Decisions

| # | Decision | Call | Rationale |
|---|---|---|---|
| 1 | **Source tier** | **OWM Classic free tier only.** Current Weather, 5day/3h Forecast, Air Pollution (incl. history), Geocoding. | 60 calls/min, 1M calls/month, **no card on file, no paid escalation path, no expiry.** Planned usage is ~29k calls/month = **2.9% of cap**. |
| 2 | **One Call 3.0/4.0** | **Deliberately excluded.** | It requires a card to activate and is PAYG at $0.0015/call beyond 1,000/day — structurally identical to the DigitalOcean and Snowflake real-money risk points, and the **only one of the three that is avoidable by design.** Excluding it removes a whole risk class. Additionally: One Call's advantage is 48h *hourly* resolution, but Hindcast's analytical hook is **long-lead decay**, for which Classic's **120h horizon beats One Call's 48h**. The constraint and the design agree — this is not a compromise. |
| 3 | **Ingestion tooling** | **Hand-rolled extractor** (~250 LOC: `httpx` + `tenacity` + `pydantic`). | The Spotify justification (OAuth/PKCE, cursor quirks) is **gone** — OWM auth is a query param. Re-evaluated fresh: **`dlt` is a genuinely reasonable alternative here and is recorded as the named runner-up in ADR-003.** Hand-rolled still wins for one decisive reason: **OWM's forecast response contains no authoritative model-run timestamp.** `issued_at` — the field the entire lead-time analysis is built on — must be *minted by the extractor* and written into an immutable request envelope alongside a payload hash. That is domain logic a transport library doesn't own, and once you're writing it, dlt buys you ~40 lines of HTTP. Secondary: zero added dependency surface on a droplet already running Airflow + Spark. |
| 4 | **Flagship modeling artifact** | **Accumulating snapshot fact** (`fct_forecast_slot`), not SCD Type 2. | The domain's natural shape is "a row whose truth fills in over time," which is textbook accumulating snapshot. See #5. |
| 5 | **SCD Type 2** | **Rejected on `dim_location` (base). Accepted on one narrow mini-dimension, `dim_location_regime`.** | Location name/lat/lon/country **do not change** — SCD2 there would be theater, the same way Great Expectations and Airbyte were refused in the original plan. But there *is* one defensible candidate, structurally identical to the old `dim_artist` banded-popularity justification: a **derived, banded `forecastability_tier`** (High/Medium/Low, from trailing-90-day skill) plus `thermal_regime` band. These genuinely drift seasonally and answer a real as-of question — *"when we issued this forecast, what did we believe this location's predictability was?"* Modeled as an **SCD2 mini-dimension / outrigger**, not by SCD2-ing the base dimension, to avoid row explosion on static attributes. Explicitly secondary to #4. |
| 6 | **DST / timezone offset** | Store **IANA tz name in `dim_location` (Type 1)**; compute local time in transform. Do **not** SCD2 the UTC offset. | OWM returns a `timezone` offset that flips with DST. That is a *time-varying fact attribute*, not a dimension change. SCD2-ing it would produce two rows per city per year that mean nothing. Trap correctly avoided. |
| 7 | **Spark's role** | **Honestly over-provisioned. Kept for skill demonstration + one genuinely Spark-shaped workload.** | Real volume: ~4.7k rows/day, ~30–60 MB/month Parquet. DuckDB territory. **But** bronze→silver is a real `explode()` of a 40-element array-of-structs per response, followed by a **window function over (location, valid_ts) ordered by issued_at** to pick lead-time milestones — that is a shuffle-heavy job that reads naturally in Spark, plus Delta `MERGE` for idempotent upserts. Backed by a **synthetic 250–500M-row benchmark** (§5, Phase 4) and an honest **counter-benchmark** showing DuckDB beating Spark ~40× at real volume. |
| 8 | **dbt targets** | **Dual target from day one: `duckdb` (dev, default) + `snowflake` (prod).** | Serves three purposes at once: keeps the Snowflake 30-day trial clock unstarted until Week 6, gives free unlimited local CI, and *is* the post-trial zero-cost fallback. Build it once, use it three ways. |
| 9 | **Actual-matching rule** | Nearest observation within **±90 min** of `valid_ts`; store `match_offset_minutes` on the fact. | Forecast slots are on exact 3h UTC boundaries; observations are not. Equality join is impossible. Tolerance is half a slot so matches are unambiguous. Offset is **stored, not hidden**, and dbt-tested — imprecision must be measurable. |
| 10 | **Measure semantics** | Secondary windowed aggregate stored alongside the point actual. | Temperature is non-additive (averageable only); precipitation is fully additive and must be **summed** over a window, not averaged. Both stored; §6 has the full additivity table. |
| 11 | **Headline metric** | **Skill score vs. persistence baseline**, not raw MAE. | `Skill = 1 − MSE_forecast / MSE_persistence`. An accuracy number without a baseline is not analysis. Brier score for POP, CSI for rain/no-rain. |
| 12 | **Cold-start backfill** | **OWM Air Pollution *history* endpoint** (free, back to 2020-11-27). | Gives a genuine multi-year historical fact table on day one so the warehouse is not empty while forecast data accrues, and enables a non-generic secondary analysis (wind/inversion vs. PM2.5). |
| 13 | **Open-Meteo** | **Optional Phase 10 enrichment. Not in the core path.** | Fully free, no key, and — critically — it archives *past forecast runs* as well as ERA5 actuals, which would allow backfilling real predicted-vs-actual pairs years deep. Genuinely tempting, deliberately deferred: the user asked for OWM and has the key, and Hindcast's "the pipeline creates the dataset" story is *stronger* without a shortcut. Documented as the named future extension. |
| 14 | **$0 accrual fallback** | **GitHub Actions scheduled workflow** as a droplet-down ingestion path. | Public repo = unlimited free minutes. If the droplet must be destroyed mid-build, a 3-hourly cron keeps writing raw envelopes to ADLS. Caveat handled by design: free-tier GH cron is delayed/skipped under load, which would corrupt lead-time buckets *if the schedule were assumed* — it isn't, because `issued_at` is always recorded, never inferred (see #3). |
| 15 | **Trial-clock risk** | **Spotify Premium clock is eliminated entirely.** No replacement clock introduced. | OWM Classic never expires and never asks for a card. Net risk points drop from three to two. See §10. |
| 16 | Kubernetes / Airbyte / Fivetran / Meltano / Great Expectations | **Still excluded.** | Unchanged reasoning. dbt tests + `dbt-expectations` + `elementary-data`, with Pandera only at the Spark bronze→silver boundary. |

## 3. Architecture Overview

*(Substantively unchanged from the original plan except the source; kept tight.)*

```
OpenWeatherMap Classic API
  ├─ /data/2.5/weather          (every 30 min × N locations)
  ├─ /data/2.5/forecast         (every  3 hr × N locations, 40 timesteps each)
  ├─ /data/2.5/air_pollution    (hourly) + /history (one-off backfill to 2020)
  └─ /geo/1.0/direct            (one-off, location seeding)
                │
                ▼   hand-rolled Python extractor, token-bucket limited to 60/min
   ADLS Gen2  ▸ bronze/   immutable raw JSON envelopes
                          {payload, requested_at(=issued_at), url, status,
                           payload_sha256, extractor_version, run_id}
                          partitioned dt=YYYY-MM-DD/hh=HH/endpoint=…
                │
                ▼   PySpark 3.5 + delta-spark 3.2  (WSL2 locally / Docker on droplet)
   ADLS Gen2  ▸ silver/   Delta tables: explode → flatten → Pandera validate →
                          dedup on (location, endpoint, source_dt) → MERGE
                │
                ▼   COPY INTO via external stage
   Snowflake  ▸ RAW → dbt staging → intermediate → marts (Kimball star)
                │           ↑ dbt-core, dual target (duckdb dev / snowflake prod)

   Power BI Desktop (import mode) ← marts + Elementary run artifacts
```

### Phase 2 — Ingestion *(Week 2, ~14h)* — **CRITICAL PATH: GO LIVE BY END OF WEEK 2**

**Goal:** raw envelopes landing in ADLS on schedule, forever, from the earliest possible date.

**Deliverables**
- `ingestion/hindcast_extract/` — a small, typed, boring package:
  - `client.py` — shared `httpx.Client`, token-bucket limiter at 50 req/min (buffer under the 60 cap), `tenacity` retry with exponential backoff + jitter on 5xx/429, hard fail on 401.
  - `models.py` — Pydantic models for each of the four endpoint responses. Validation failures are **logged and the raw payload is still written**, never dropped — bronze is immutable and lossless by contract.
  - `envelope.py` — writes the canonical record:
    ```json
    { "run_id":"…", "endpoint":"forecast", "location_id":"oshawa_ca",
      "requested_at":"2026-08-04T15:00:03.412Z",   // ← this IS issued_at
      "http_status":200, "url_redacted":"…appid=***",
      "payload_sha256":"…", "extractor_version":"1.4.2",
      "image_digest":"sha256:…", "payload":{ … } }
    ```
  - `runners/` — `current.py`, `forecast.py`, `air_quality.py`, `air_quality_backfill.py`, `geocode_seed.py`.
- **Forecast model-run deduplication:** because OWM refreshes the forecast on its own cadence, two polls 3h apart can return the *same underlying model run*. Compare `payload_sha256` against the previous poll for that location and set `is_new_model_run`. This is recorded, not filtered — knowing the forecast *didn't* update is itself a finding, and it means "lead time" and "number of distinct model runs" are different axes.
- **Air Pollution history backfill:** one-off run pulling hourly AQI from 2020-11-27 to present for all locations. ~12 locations × ~1,900 days × 24h ≈ 550k rows, fetched in ~1,000 calls. **Gives a non-empty warehouse from day one.**
- Bronze layout: `bronze/endpoint={e}/dt={YYYY-MM-DD}/hh={HH}/{location_id}_{run_id}.json.gz`
- Interim scheduling: `systemd` timers on the droplet (Airflow arrives Week 3). **Do not wait for Airflow to start collecting.**

**Call budget**

| Stream | Cadence | Calls/day |
|---|---|---|
| Current weather × 12 | every 30 min | 576 |
| Forecast × 12 | every 3 h | 96 |
| Air pollution × 12 | hourly | 288 |
| **Total** | | **960 (≈29k/mo = 2.9% of the 1M cap)** |

**Key decisions**
- 30-min current-weather cadence vs. OWM's ~10-min refresh: 30 min guarantees an observation within ±15 min of every 3-hour boundary, comfortably inside the ±90 min matching tolerance, at a fifth of the call cost of 10-min polling. Deliberate, documented in ADR-004.
- Bronze is **append-only and never rewritten.** Every reprocessing bug is fixable by replaying bronze.

**Demo line:** *"Ingestion went live in week two and never stopped. The forecast archive it built doesn't exist anywhere else — OpenWeatherMap doesn't sell you their own past predictions."*

### Phase 3 — Orchestration *(Week 3, ~12h)*

**Goal:** Airflow 3.x owns the schedule; systemd timers retired.

**Deliverables**
- Airflow 3.x via Docker Compose (`api-server`, `scheduler`, `dag-processor`, `triggerer`, `worker`), `LocalExecutor`, metadata on Azure Postgres.
- DAGs:

| DAG | Schedule | Purpose |
|---|---|---|
| `owm_current_ingest` | `*/30 * * * *` | Fan-out over locations via dynamic task mapping |
| `owm_forecast_ingest` | `0 */3 * * *` | 12 mapped tasks, one per location |
| `owm_air_quality_ingest` | `@hourly` | " |
| `bronze_to_silver_spark` | `@hourly` | `SparkSubmitOperator` |
| `silver_to_snowflake` | `0 * * * *` | `COPY INTO` from external stage |
| `dbt_build` | `15 * * * *` | `dbt build --target snowflake` |
| **`close_forecast_slots`** | `@daily 02:00 UTC` | **Finalizes accumulating-snapshot rows whose `valid_ts` is >24h past.** The distinctive DAG in this project. |
| `elementary_report` | `@daily` | DQ report → ADLS |
| `dvc_snapshot` | `@weekly` | Tag + push a data version |

- **Airflow Assets** (3.x) chaining ingest → spark → warehouse rather than cross-DAG sensors.
- Deferrable operators where waiting is involved; SLA misses → Datadog event + Sentry.
- `catchup=False` on all ingest DAGs — **replaying a missed weather poll is meaningless**, the moment is gone. Explicit and documented; it's a genuine domain constraint, not laziness.

**Key decisions**
- **Idempotency contract:** every task keyed on `(logical_date, location_id, endpoint)`; re-running overwrites the same bronze path. Safe to re-run anything, always.
- On-call reality check: a missed 3-hour forecast poll creates a *hole in a lead-time bucket*, not a lost row. The pipeline must record the hole (see `dq_status` in §6), not silently interpolate over it.

**Demo line:** *"Nine DAGs, asset-driven, fully idempotent — and one of them is a slot-closure job that finalizes accumulating-snapshot rows, which is a genuinely uncommon thing to see running in Airflow."*

### Phase 4 — Transformation (Spark) *(Week 4, ~14h)*

**Goal:** bronze JSON → validated, deduplicated silver Delta tables.

**Deliverables**
- `transform/spark/jobs/`:
  - `bronze_current_to_silver.py` — flatten `main`/`wind`/`clouds`/`rain`/`snow`/`sys` structs; unit normalization; dedup on `(location_id, source_dt)` keeping first-seen.
  - `bronze_forecast_to_silver.py` — **the real Spark job**: `explode(payload.list)` → 40 rows per response → flatten → derive `lead_time_minutes = valid_ts − issued_at` → dedup on `(location_id, issued_at, valid_ts)` → Delta `MERGE`.
  - `bronze_air_quality_to_silver.py`
  - `silver_forecast_milestones.py` — the shuffle-heavy one: `Window.partitionBy(location_id, valid_ts).orderBy(lead_minutes)` with `row_number()` per lead-time milestone band. This is what justifies Spark.
- **Pandera** schemas at the bronze→silver boundary only (the one place dbt cannot reach): range checks (`temp_c` ∈ [−90, 60], `humidity_pct` ∈ [0,100], `wind_deg` ∈ [0,360), `pop` ∈ [0,1]), nullability, and a **cross-field check that `valid_ts > issued_at`** — a violation there would silently poison every lead-time bucket, so it's a hard-fail.
- Delta tables in `silver/`: `obs_weather`, `fct_forecast_issue_raw`, `obs_air_quality`. `OPTIMIZE` + `ZORDER BY (location_id, valid_ts)` weekly.

**The synthetic-scale benchmark** (`docs/architecture/spark-scale-benchmark.md`)

| | |
|---|---|
| **Synthetic dataset** | 1,000 cities × 90 days × 8 issues/day × 40 timesteps ≈ **288M forecast rows (~9 GB Parquet)**, generated with realistic diurnal + seasonal signal and deliberate skew (3 "mega-cities" holding 20% of rows) |
| **Workload benchmarked** | The real `silver_forecast_milestones` window job, not a synthetic word-count |
| **Dimensions measured** | partitioned vs. unpartitioned; ZORDER on/off; AQE on/off; broadcast vs. sort-merge join to dims; salted vs. unsalted skew handling; shuffle bytes + spill + wall clock |
| **Counter-benchmark (the honest half)** | The same job in **DuckDB at real production volume** (~140k rows/month) — expected to beat Spark by roughly an order of magnitude on wall clock |
| **Stated conclusion** | *"At Hindcast's real volume Spark is the wrong tool and DuckDB is ~40× faster. Spark is in this stack for two reasons: the bronze→silver explode-and-window is genuinely Spark-shaped, and I wanted to demonstrate I can tune it. Here is the crossover point I measured, at roughly 40M rows."* |

**Demo line:** *"I benchmarked my own architecture and published the point at which my tool choice starts being correct — and it's well above my actual data volume."*

### Phase 5 — Warehouse Modeling *(Weeks 5–6, ~22h)* — the intellectual core

**Goal:** the star schema of §6, built and tested.

**Week 5 — build entirely against DuckDB.** No Snowflake account exists yet. All staging, intermediate, and mart models developed with `--target duckdb` against silver Parquet read directly via `read_parquet()`.

**Week 6 — sign up for Snowflake** (30-day trial, no card, XS warehouse, `AUTO_SUSPEND=60`), create the external stage against ADLS, `COPY INTO` RAW, and run `dbt build --target snowflake`. Trial then covers Weeks 6–10, spanning BI work and demo capture, with margin.

**dbt layer structure**
```
models/
  staging/       stg_owm__current.sql, stg_owm__forecast.sql,
                 stg_owm__air_quality.sql, stg_seed__locations.sql
                 (1:1 with source, rename/cast/UTC-normalize only)
  intermediate/  int_forecast_with_leadtime.sql
                 int_observation_slot_matched.sql   ← the ±90min matching logic
                 int_forecast_milestone_pivot.sql   ← lead-time milestone selection
                 int_persistence_baseline.sql       ← the baseline predictor
                 int_location_regime_bands.sql      ← feeds the SCD2 mini-dim
  marts/
    core/        dim_date, dim_time, dim_location, dim_location_regime,
                 dim_weather_condition, dim_lead_time_bucket,
                 dim_air_quality_band, dim_pipeline_run
    facts/       fct_weather_observation, fct_forecast_issue,
                 fct_forecast_slot (accumulating snapshot, incremental/merge),
                 fct_forecast_error (long, BI-serving),
                 fct_air_quality_observation
```

**Key decisions**

## 6. Star Schema Design

### 6.1 The three-fact architecture

| Fact | Type | Grain | Rows/day (12 loc) |
|---|---|---|---|
| `fct_weather_observation` | Transaction | **One row per location per distinct source observation timestamp (`dt`)** | ~576 |
| `fct_forecast_issue` | Transaction (append-only ledger) | **One row per (location, forecast issue timestamp, valid timestamp)** — one predicted timestep from one API response | ~3,840 |
| **`fct_forecast_slot`** | **Accumulating snapshot** | **One row per (location, valid timestamp)** — created on first appearance, rewritten ~40×, closed once | ~96 new/day |
| `fct_forecast_error` | Transaction (derived, BI-serving) | **One row per (location, valid timestamp, lead-time milestone)** — one comparison pair | ~768 |
| `fct_air_quality_observation` | Transaction | One row per (location, hour) | ~288 + 550k backfill |

`fct_forecast_error` is **derived from `fct_forecast_slot` by unpivot**, so there is exactly one source of truth. The snapshot is the pipeline's state machine and the modeling showpiece; the long fact is the query surface. Both are justified; neither is redundant.

*Design alternative considered and rejected:* build only `fct_forecast_issue` + `fct_forecast_error` and skip the wide snapshot. Rejected because the snapshot is what tracks **slot lifecycle state** (`pending` → `awaiting_actual` → `closed`), which is what the `close_forecast_slots` DAG operates on and what Page 4 of the report visualizes. Dropping it would mean recomputing lifecycle state on every query.

### 6.2 `fct_forecast_slot` — the flagship

**Grain: one row per (location, valid_timestamp_utc).** A row is born the first time a 5-day forecast mentions that slot (~120h before it happens) and dies the day after it occurs.

| Column group | Columns |
|---|---|
| Keys | `forecast_slot_key` (SK), `location_key`, `location_regime_key` *(SCD2, as-of first forecast)*, `valid_date_key`, `valid_time_utc_key`, `valid_time_local_key` *(role-playing)*, `pipeline_run_key` *(audit dim)* |
| Degenerate | `valid_ts_utc`, `location_id` |
| **Milestone predictions** (×8: 120/96/72/48/24/12/06/03h) | `temp_fcst_{L}h`, `pop_fcst_{L}h`, `wind_speed_fcst_{L}h`, `condition_key_fcst_{L}h`, `issued_at_{L}h`, `actual_lead_hours_{L}h` |
| **Actuals** | `temp_actual_c`, `pop_actual_binary`, `precip_actual_mm`, `wind_speed_actual_ms`, `wind_deg_actual`, `condition_key_actual`, `actual_obs_ts`, `match_offset_minutes` |
| Secondary actual | `temp_actual_window_mean_c`, `precip_actual_window_sum_mm`, `obs_count_in_window` |
| Baseline | `temp_persistence_c` *(value 24h before valid_ts)*, `pop_persistence` |
| Lifecycle | `first_forecast_at`, `last_forecast_at`, `revision_count`, `distinct_model_runs`, `slot_status`, `slot_closed_at`, `dq_status` |
| Derived errors | `abs_err_temp_{L}h`, `signed_err_temp_{L}h`, `sq_err_temp_{L}h`, `brier_{L}h`, `wind_dir_circ_err_{L}h` |

`slot_status` ∈ `{pending, forecasting, awaiting_actual, closed, closed_no_actual}`.
`dq_status` ∈ `{ok, sparse_forecasts, wide_match_offset, no_actual, ingest_gap}`.

**This is a textbook accumulating snapshot**: fixed row population determined at slot creation, milestone columns filling progressively, rows rewritten in place, one final closure event. It is a *harder* pattern to implement correctly than SCD2 and it is far less commonly seen in portfolio work.

### 6.3 The two hard mechanics — worked out, not hand-waved

#### (a) Milestone selection: which forecast counts as "the 24-hour forecast"?

Polls happen every 3 hours, so no forecast is ever issued at exactly T−24h. Rule:

> For milestone **L**, select the forecast issue for that (location, valid_ts) whose `lead_time_hours` is the **smallest value ≥ L** — i.e. the last forecast issued *before* the L-hour mark. Formally: `WHERE lead_hours >= L AND lead_hours < L + 3` then `QUALIFY ROW_NUMBER() OVER (PARTITION BY location_key, valid_ts, milestone ORDER BY lead_hours ASC, issued_at DESC) = 1`.

Choosing `≥ L` rather than "nearest" is deliberate: it guarantees the reported figure is **never more informed than the label claims**. A "24h forecast" that was actually issued 23h out would flatter the accuracy curve. This is a conservative, defensible convention and it is documented as such.

`actual_lead_hours_{L}h` is stored on every milestone so the imprecision is auditable rather than hidden, and it is dbt-tested to fall in `[L, L+3)`. If a poll was missed, the milestone is `NULL` and `dq_status = 'sparse_forecasts'` — **never backfilled from an adjacent bucket.**

#### (b) Actual matching: forecast slots are on 3h UTC boundaries, observations are not

```sql
-- int_observation_slot_matched.sql (essential logic)
SELECT
    s.location_key,
    s.valid_ts_utc,
    o.obs_ts_utc                                   AS actual_obs_ts,
    DATEDIFF('minute', s.valid_ts_utc, o.obs_ts_utc) AS match_offset_minutes,
    o.temp_c                                       AS temp_actual_c,
    o.condition_key                                AS condition_key_actual
FROM slots s
LEFT JOIN stg_owm__current o
       ON o.location_key = s.location_key
      AND o.obs_ts_utc BETWEEN DATEADD('minute', -90, s.valid_ts_utc)
                           AND DATEADD('minute',  90, s.valid_ts_utc)
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY s.location_key, s.valid_ts_utc
    ORDER BY ABS(DATEDIFF('second', s.valid_ts_utc, o.obs_ts_utc)) ASC,
             o.obs_ts_utc ASC          -- deterministic tie-break
) = 1
```

- **±90 minutes** = half a 3-hour slot, so tolerance windows never overlap and no observation can be claimed by two slots.
- `LEFT JOIN`, so a missing observation produces `slot_status='closed_no_actual'` rather than silently dropping the row. Excluded from accuracy aggregates, retained in the table, counted in the SLI.
- **Secondary windowed measures** are computed alongside: `temp_actual_window_mean_c` (mean of all observations in the window — statistically smoother for temperature) and `precip_actual_window_sum_mm` (**summed**, because precipitation is additive and averaging it is simply wrong). Reporting the point actual as primary and the windowed value as secondary lets the report demonstrate the two produce nearly identical MAE, which is itself a validation of the matching rule.
- **Wind direction** needs circular arithmetic: `err = MIN(|a−b|, 360−|a−b|)`. Naïve subtraction reports a 2° miss between 359° and 1° as 358°.

### 6.5 The SCD2 question, answered honestly

**Where SCD2 does not belong — stated plainly:**

`dim_location`'s real attributes (name, coordinates, country, timezone identifier) are **static**. Oshawa will not move. Forcing SCD2 onto them would produce a dimension with `valid_from`/`valid_to` columns and exactly one version per row forever — a costume, not a design. The original plan refused to bolt on Great Expectations and Airbyte because they weren't earned; the same standard applies here.

`dim_weather_condition` is a fixed vendor enum. `dim_lead_time_bucket` and `dim_air_quality_band` are configuration. None warrant SCD2.

**Where SCD2 genuinely is earned — `dim_location_regime`:**

There is one real candidate, and it is structurally identical to the `dim_artist` banded-popularity SCD2 from the original plan: a **derived, banded attribute that drifts, and whose historical value changes how you read a fact.**

- `forecastability_tier` — each location's trailing-90-day temperature skill score, banded High / Medium / Low.
- `thermal_regime` — trailing-30-day mean temperature, banded Cold / Cool / Mild / Warm / Hot.
- `volatility_band` — trailing-30-day stddev of day-over-day temperature change.

These change on a seasonal cadence, and they answer a genuine as-of business question: **"When we issued this forecast, what did we believe this location's predictability was — and were we right?"** Without SCD2, every historical forecast is scored against today's belief about the city, which retroactively rewrites the past. That is exactly the failure SCD2 exists to prevent.

Two design choices make it defensible rather than gratuitous:

1. **Mini-dimension, not base-dimension SCD2.** The static attributes stay in `dim_location` (Type 1, 12 rows). Only the drifting derived attributes live in `dim_location_regime` (Type 2, maybe 150 rows/year). Facts carry both FKs. This is the standard Kimball answer for "a few volatile attributes on an otherwise static dimension," and it avoids re-versioning `lat`/`lon` every time a temperature band flips.
2. **Banded, not continuous.** Storing raw trailing skill would create a new version every single day. Banding is what makes SCD2 tractable — the same reasoning that made banded popularity work for `dim_artist`.

**Priority, stated explicitly:** `dim_location_regime` is **Phase 5b and optional.** If Week 6 runs short, cut it. `fct_forecast_slot` is not optional.

**And the framing that matters:** the accumulating snapshot is not a *consolation prize* for a domain that resists SCD2. It is the harder artifact. SCD2 tracks how a *descriptor* changed; an accumulating snapshot tracks how a *process* unfolded, requires in-place MERGE semantics, a lifecycle state machine, an explicit closure job, and careful late-arriving-data handling. If a reviewer only has time to look at one table in this repo, `fct_forecast_slot` is the one to point them at.

### 6.6 Measure additivity

| Measure | Additivity | Correct aggregation | Wrong aggregation to avoid |
|---|---|---|---|
| `temp_actual_c`, `temp_fcst_*` | **Non-additive** | AVG / MIN / MAX only | Never SUM |
| `precip_actual_mm` | **Fully additive** | SUM across time and location | Never AVG over a window |
| `pressure_hpa`, `humidity_pct` | **Semi-additive** | AVG over time; never SUM | SUM over time |
| `abs_err_temp_*` | Additive numerator | `AVG` → MAE | — |
| `sq_err_temp_*` | Additive numerator | `SQRT(AVG(sq_err))` → RMSE | **Never AVG of pre-computed RMSEs** |
| `brier_*` | Additive numerator | AVG of squared prob error | Never AVG of pre-computed Brier scores |
| `revision_count` | Additive | SUM / AVG | — |
| `wind_deg` | **Circular** | Vector mean, or circular error | Never arithmetic mean or plain difference |

This table goes verbatim into `bi/measures.md` and into the dbt model docs. Three of the seven rows are traps that a careless Power BI model would fall into.

## 7. ETL Pipeline Versioning — Four Layers

*(Conceptually unchanged from the original plan; the source swap doesn't touch it.)*

| # | Layer | Mechanism | Restore procedure |
|---|---|---|---|
| 1 | **Infrastructure** | Terraform + remote state in Terraform Cloud; state versions retained | `terraform apply` at a given state serial |
| 2 | **Code / pipeline** | DAGs, Spark jobs, extractor, dbt project **baked into Docker images**, never git-synced. `git tag vX.Y.Z` → Buildx → GHCR → **image digest** recorded in `deploy/manifest.json` | `deploy.yml` with tag → resolves to digest → `docker compose up` |
| 3 | **Data** | **DVC** + Azure Blob remote; weekly `data-vYYYY.WW` tags; `dvc.yaml` stages make `dvc repro` a real path | `git checkout data-v… && dvc pull` |
| 4 | **Warehouse** | Snowflake **Time Travel** (trial default 1 day; `AT(TIMESTAMP=>…)` and `UNDROP`) + dbt snapshots on marts | `CREATE TABLE … CLONE … AT(OFFSET => -3600)` |

**What ties the four together — the run-audit table.** `dim_pipeline_run` carries `git_tag`, **`image_digest`**, `dvc_data_version`, `extractor_version`, and `run_id`, and **every fact row carries `pipeline_run_key`**. So this is answerable in one query:

```sql
-- "Which code built this row, from which data version, on which infrastructure?"
SELECT r.git_tag, r.image_digest, r.dvc_data_version, r.started_at, COUNT(*)
FROM   fct_forecast_slot f
JOIN   dim_pipeline_run  r USING (pipeline_run_key)
WHERE  f.valid_ts_utc::date = '2026-08-15'
GROUP  BY 1,2,3,4;
```

**Why baked images, not git-sync:** `git pull` on the droplet means the running pipeline's identity is "whatever `main` was at the moment the scheduler happened to reload," which is unreproducible and untestable. A digest is immutable, signed, SBOM'd, and rollback-able in one command. The reproducibility claim is only as strong as its weakest layer, and git-sync would be the weak one.

| 3 | ~~**Spotify Premium** trial clock~~ | ✅ **ELIMINATED** | See below |

### Risk point 3 is gone — and no replacement clock was introduced

The Spotify-era plan carried a genuinely nasty constraint: `/me/*` endpoints required the developer account to hold **active Premium**, so a 30-day Premium trial had to be started, tracked, and burned inside a build window — and cancelled before it billed. That created a hard, irreversible countdown coupled to the *data source itself*, which is the worst place for a clock, because unlike compute you cannot rebuild lost history.

**OpenWeatherMap's Classic free tier introduces no equivalent clock:**

- **No card is required** to hold or use a Classic key.
- **The tier does not expire** — it is not a trial, it is the permanent free plan.
- **There is no paid escalation path attached to it.** Exceeding 60 calls/min returns HTTP 429; exceeding 1M calls/month suspends the key. Neither generates a bill. **The failure mode is throttling, not charging** — which is exactly the failure mode you want under a $0 constraint.
- Planned usage is **2.9% of the monthly cap**, monitored in Datadog with an alert at 25%.
- **One Call 3.0/4.0 — the one OWM product that *would* reintroduce a card-on-file PAYG clock — is deliberately excluded** (§2, decision #2). This is the whole reason for that decision.

Net effect: risk points drop from three to two, and the one that disappeared was the only one that could destroy *data* rather than merely cost money. The remaining two are both infrastructure-side, both bounded by credit, both alertable, and both resolved by `terraform destroy`.

### Zero-cost mode (post-build steady state)

The user does not need anything to stay live after the build. On completion:

1. `terraform destroy` on the DigitalOcean workspace (droplet + reserved IP) and on Azure PostgreSQL. Airflow is gone; nothing was stored on it.
2. Export all marts to Parquet → `data/exports/`, `dvc push`, tag `data-final`. Also attach a compressed Parquet bundle to a **GitHub Release** so the repo is self-contained even if ADLS is deleted.
3. Flip dbt to `--target duckdb`, pointed at the committed Parquet. `dbt build` still runs green, locally, in CI, forever, for $0. **The full star schema remains reproducible by anyone who clones the repo** — which is exactly what a reviewer will try.
4. Repoint the `.pbix` at the DuckDB/Parquet extract; commit both the `.pbix` and full-page PNG exports so the report is viewable without Power BI installed.
5. Optionally leave `accrual-fallback.yml` running: 3-hourly ingestion from GitHub's free runners into ADLS costs $0 in compute and pennies in storage, and the dataset keeps growing while the project sits on the résumé. **This is the one thing OWM's card-free, non-expiring tier makes possible that the Spotify design never could have.**
6. Cancel nothing, because nothing was ever started that bills.

## 11. Portfolio Presentation

### The 30-second version

> "I built a lakehouse that grades the weather forecast. Every three hours it snapshots the 5-day forecast for a dozen cities I have a personal connection to, every thirty minutes it records what actually happened, and it joins the two to measure how forecast accuracy decays with lead time. The centrepiece is an accumulating snapshot fact table — one row per city per future 3-hour slot, rewritten about forty times as the forecast is revised, then closed when the actual lands. ### The five things to lead with

1. **"The dataset doesn't exist anywhere else."** OpenWeatherMap does not sell you their own past forecasts. The forecast archive is *created by the act of running the pipeline*. That makes orchestration reliability load-bearing — a missed poll is a permanently missing data point, not a re-runnable task. It also means `catchup=False` on ingest DAGs is a domain decision, not a default.
2. **"I used an accumulating snapshot, and here's why SCD2 would have been fake."** Walk through §6.5. Explicitly saying *"I looked for an SCD2 candidate, and the honest answer for the base location dimension was no — here's what I built instead, and here's the one narrow mini-dimension where SCD2 genuinely is earned"* demonstrates judgment far more than a bolted-on Type 2 would.
3. **"I benchmarked my own architecture and published where my tool choice becomes correct."** The Spark benchmark plus the DuckDB counter-benchmark, with the measured ~40M-row crossover. Volunteering that your stack is over-provisioned for your data — with numbers — is the single most senior-sounding thing in the project.
4. **"Accuracy without a baseline isn't analysis."** Skill score vs. persistence, Brier score with decomposition, CSI on the contingency table. This is real forecast verification methodology, not a bar chart of temperatures.
5. **"Four layers of versioning, and I can query all four from SQL."** Show the `dim_pipeline_run` join in §7.

### Résumé bullets

- Built an end-to-end lakehouse (Airflow 3 · PySpark 3.5 · Delta Lake · dbt · Snowflake) on Terraform-managed DigitalOcean + Azure infrastructure, ingesting **~29k API calls/month across 4 endpoints and 12 locations** at **$0 total cost** under student credits and permanently-free tiers.
- Designed a Kimball star schema whose flagship is an **accumulating snapshot fact table** tracking forecast→revision→actual lifecycle at ~40 revisions per row, implemented as an incremental dbt `MERGE` with an Airflow-driven slot-closure job and a 5-state lifecycle machine.
- Engineered a **±90-minute temporal matching join** between 3-hour-boundary forecast slots and irregularly-timed observations, with the match offset persisted and dbt-tested rather than hidden — plus conservative lead-time milestone selection that never reports a forecast as more informed than its label.
- Implemented **four-layer reproducibility** (Terraform state · immutable Docker image digests · DVC data versions · Snowflake Time Travel) unified by an audit dimension joined to every fact, making "which code and which data produced this row" a single SQL query.

### Critical path

```
Phase 1 (infra) ──▶ Phase 2 (INGEST LIVE, end Wk2) ──▶ [8 weeks of wall-clock accrual] ──▶ Phase 9 (BI)
                            │
                            └──▶ Phases 3–8 run IN PARALLEL with accrual
```

**The one scheduling insight that governs this plan:** Phases 3–8 do not depend on how much data exists — they depend on data *arriving*. Phase 9 depends on data *volume*, which is a function of calendar time, not effort. **Every day ingestion is delayed is a day permanently subtracted from the analysis, and it cannot be bought back with extra hours later.** This is the structural difference from the Spotify design, where `recently-played` delivered history on day one.

Therefore: if Week 1 slips, **cut scope from Phase 1, not from Phase 2.** A hand-provisioned droplet running the extractor on a systemd timer, Terraform-ified in Week 3, is strictly better than a beautifully IaC'd platform that starts collecting a week late.
